## 一、代码质量提升（高优先级）

### 1.1 PLC0415 导入提升 🔴

**现状**: 593 处 `import` 在函数/方法内部，每次调用都重新 import，影响性能和可读性。

**重点文件**:
| 文件 | 数量 |
|------|:----:|
| `agents/editor.py` | 23 |
| `api/routers/` | 多个 |
| `agents/architect.py` | 4 |
| `agents/base.py` | 1 |

**方案**: 将可安全提升的 import 移至文件顶部。对于有循环导入风险的，使用 `TYPE_CHECKING` 守卫。

### 1.2 E741 模糊变量名修复 🟡

**现状**: 33 处使用 `l` 作为变量名（易与 `1`/`I` 混淆）。

**重点文件**: `worlds/atlas.py` (11)、`dialogue/` (9)、`quality/engine.py` (3)

**方案**: 将 `l` 重命名为 `loc`、`line`、`item` 等语义化变量名。

### 1.3 annotations 收尾 🟡

**现状**: 14 个文件仍缺失 `from __future__ import annotations`。

**缺失文件**: `api/routes.py`, `api/routers/admin.py`, `api/routers/audit.py`, `api/routers/gacha.py`, `api/routers/genres.py`, `api/routers/search.py`, `api/routers/usage_routes.py`, `api/routers/ws.py`, `audit/gates/_base.py`, `config/database.py`, `config/llm.py`, `config/pipeline.py`, `config/thresholds.py`, `conflict/engine.py`

## 二、性能优化（中优先级）

### 2.1 `list()` 包装消除 🟡

**现状**: 35 处 `list(dict.values())` / `list(dict.keys())` 不必要的中间列表（Python 3 中 `.values()`/`.keys()` 已是视图，可直接迭代）。

**重点文件**: `worlds/atlas.py` (4)、`aigc_detect/engine.py` (3)、`character/engine.py` (2)、`notify/engine.py` (2)

**方案**: 删除不必要的 `list()` 包装，仅在需要索引/切片时保留。

## 六、自用优化分析（个人用户视角）v4

> 从单机个人用户的视角，分析当前项目在「自用」场景下的问题与优化方向。
> 核心原则：**零成本优先、一键启动、写作为王、去掉噪音**。

---

### 6.1 当前定位 vs 自用需求

| 维度 | 当前状态 | 自用需求 | 差距 |
|------|----------|----------|:----:|
| **基础设施** | 4 个 Docker 服务 (Neo4j/Redis/NATS/Qdrant) | 零依赖启动（SQLite 内置） | 🔴 |
| **模型成本** | 默认 DeepSeek API（按量付费） | 本地 Ollama 优先（免费） | 🟡 |
| **启动流程** | 配置 .env → Docker → 4 服务 → uvicorn → 前端 | 一键启动 | 🟡 |
| **前端 UI** | VS Code 风格 IDE（13 个侧面板） | 简洁写作界面 | 🟢 |
| **功能范围** | 多 Agent 协作/插件系统/实时协作/多平台发布/社区 | 核心写作管线 | 🟡 |
| **配置复杂度** | 149 行 .env.example，50+ 配置项 | 3-5 项关键配置 | 🔴 |
| **系统资源** | Neo4j(2GB) + Redis(256MB) + Qdrant(512MB) + NATS(128MB) | 仅 Python 进程 | 🔴 |

### 6.2 自用场景核心问题

#### 问题 1：基础设施过重 🔴

```
当前：Docker Desktop → Neo4j + Redis + NATS + Qdrant（~3GB 内存）
理想：pip install → python kunlun_cli.py up（零外部服务）
```

**分析**：
- Neo4j 是唯一「难替代」的服务（图查询 Cypher 独有），但有 SQLite 降级
- Redis 只用于缓存和消息队列，Python 内存 dict 可替代
- NATS 用于 Agent 间通信，单进程内 asyncio.Queue 可替代
- Qdrant 用于向量检索，numpy + 内存索引可替代（小规模自用场景）

**已有降级能力**：系统已实现 SQLite graph 降级、Redis 不可用时降级到内存、NATS 不可用时降级到进程内。但**降级模式是二等公民**，有许多功能在降级时不可用。

**优化方向**：
- 将降级模式升为**默认模式**（一键启动，零外部服务）
- Docker 服务作为**可选增强**（大数据量/高性能场景）
- 启动时自动检测：无 Docker → 纯 SQLite 模式，有 Docker → 可选启用

#### 问题 2：模型成本不可控 🟡

```
当前：默认走 DeepSeek API（每章 ~0.01-0.05 元）
理想：默认走 Ollama 本地模型（免费），API 作为可选增强
```

**分析**：
- 写一本 100 章的小说，API 费用约 1-5 元（DeepSeek 便宜）
- 但质量评估（Tier 3）每次调用 deepseek-reasoner 费用更高
- 17 步管线中，审计（53 维）调用了大量 LLM，自用场景不需要这么细
- Ollama 已支持（qwen3-8b / deepseek-r1-8b / llama3.1-8b），但**只在回退链中**，不是默认

**优化方向**：
- 新增「本地模式」开关：`LLM_MODE=local` → 全部走 Ollama
- 本地模式下自动降低审计维度（53→15 维，只保留核心检查）
- 本地模式下跳过 Tier 3 级联（本地模型做不了复杂推理）
- 写一个 `kunlun setup-local` 命令自动下载 Ollama + 推荐模型

#### 问题 3：配置复杂度高 🔴

```
当前：.env.example 149 行，50+ 配置项
理想：自用只需 3 项：LLM_MODE、DEEPSEEK_API_KEY（可选）、OLLAMA_HOST（可选）
```

**分析**：
自用场景下，以下配置项**完全不需要用户关心**：
- OTEL/可观测性（OTEL_ENABLED 等）
- 速率限制（RATE_LIMIT_*）
- API 安全（API_AUTH_*）
- Telegram/飞书/企微 Webhook
- 审计门禁阈值（AUDIT_* 共 6 项）
- 管线配置（PIPELINE_* 共 6 项）
- 通知推送（TELEGRAM_* / FEISHU_* / WECOM_* / WEBHOOK_*）

**优化方向**：
- 所有配置项设置**合理默认值**，无需用户配置
- 创建 `.env.minimal` 仅 5 行：LLM_MODE / DEEPSEEK_API_KEY / LLM_LOCAL_MODEL / DATA_DIR / LOG_LEVEL
- 其余配置从 `config/defaults.py` 读取默认值

#### 问题 4：功能膨胀 🟡

```
当前：155+ Python 文件，39 子包，~44,000 行 + Phase 1/2 新增 ~8,000 行
自用核心：管线引擎 + 写作 Agent + 审计 + 知识图谱 ≈ 20,000 行
```

**自用不需要的功能**：
| 功能 | 代码量 | 自用价值 | 建议 |
|------|:------:|:--------:|------|
| 插件系统 (plugins/) | ~500 行 | 无 | 保留但默认不加载 |
| 实时协作 (collab/) | ~800 行 | 无 | 保留但默认不加载 |
| 社区模块 (community/) | ~1,200 行 | 无 | 保留但默认不加载 |
| 多平台发布 V2 (publish_v2/) | ~1,500 行 | 低 | 保留但默认不加载 |
| 通知推送 (notify/) | ~400 行 | 低 | 保留 |
| TTS (tts/) | ~350 行 | 低 | 保留但默认不加载 |
| 图像生成 (image_gen/) | ~400 行 | 低 | 保留但默认不加载 |
| 开放 API (openapi/) | ~400 行 | 低 | 保留但默认不加载 |
| 编辑器集成 | ~200 行 | 无 | 保留 |
| 数据分析看板 | ~300 行 | 低 | 保留 |

**优化方向**：
- 这些模块**不需要删除**，但默认不加载
- 通过 `kunlun up` 启动时，只加载核心管线模块
- 前端对应侧面板（13 个）默认隐藏，只显示：写作 / 大纲 / 角色 / 世界观 / 审计

#### 问题 5：前端 UI 过于复杂 🟡

```
当前：VS Code 风格 IDE → 13 个侧面板 + 10 个视图
自用：写作为主 → 3 个面板（写作 / 大纲 / 角色） + 审计面板
```

**分析**：
- ABTestView、AnalysisView、DashboardView、ExportView、ImportView、OrchestratorView、PipelineView、PromptsView、WorldView 等 9 个视图对自用场景价值有限
- 核心视图：WriteView（写作）、BooksView（书架）、SettingsView（设置）
- 侧面板：Write（写作）、Outline（大纲）、Characters（角色）、World（世界观）、Audit（审计）

**优化方向**：
- 新增「简洁模式」UI 布局
- 默认隐藏高级面板，通过「高级模式」开关显示
- 写作界面作为默认首页

#### 问题 6：Ollama 本地模型体验差 🟡

**当前状态**：
- `model_router.py` 有 3 个本地模型定义（qwen3-8b / deepseek-r1-8b / llama3.1-8b）
- 本地模型只在回退链中，不是默认选项
- 没有 `kunlun setup-local` 一键安装命令
- 没有本地模型推荐（哪个模型写中文小说最好？）
- 审计 53 维在本地模型上全部跑一遍太慢

**优化方向**：
- 新增 `kunlun setup-local` 命令：
  ```
  1. 检测 Ollama 是否安装
  2. 自动下载推荐模型：qwen3-14b（中文写作最佳）/ deepseek-r1-8b（推理）
  3. 配置 .env 为本地模式
  4. 验证模型可用
  ```
- 本地模式下自动降级审计维度：53 → 15 维核心检查
- 本地模式下跳过 Tier 3 级联评估
- 新增 `LLM_LOCAL_MODEL` 配置项，指定默认本地模型

### 6.5 自用 vs 商业化路线

| 维度 | 自用路线 | 商业化路线 |
|------|----------|------------|
| 基础设施 | SQLite 内置（零依赖） | Docker 全套服务 |
| 模型 | Ollama 本地优先 | API 优先（多 Key 轮换） |
| 配置 | 3 项必需配置 | 50+ 项可配置 |
| UI | 简洁模式（3 面板） | 完整 IDE（13 面板） |
| 功能 | 核心管线（写作/审计/知识图谱） | 全部功能（插件/协作/社区/发布） |
| 启动 | 1 命令 | docker compose up |
| 成本 | 免费（本地模型） | 按 API 用量付费 |

**核心观点**：项目应同时支持两条路线，自用路线为默认。商业化功能通过配置开关启用，不影响自用体验。
