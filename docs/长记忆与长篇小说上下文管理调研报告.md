# 长记忆项目与长篇小说上下文管理 — 深度调研报告

> **调研对象**：长记忆架构、向量数据库、知识图谱、RAG 技术在百万字长篇小说创作中的应用
> **目标引擎**：昆仑创作引擎 (kunlun v0.4.0)
> **调研日期**：2026-09-02
> **覆盖项目/技术**：60+ 个

---

## 执行摘要

本报告系统调研了六大技术领域共 60+ 个项目/技术，核心发现如下：

1. **上下文管理**：滑动窗口 + 渐进式摘要 + 分层上下文是工业界主流；昆仑已有的 6 段 WenShape/SAGA 预算分配器设计先进，但缺少"记忆分层写入"和"主动遗忘"机制。
2. **向量数据库**：Qdrant 在延迟、过滤精度和自托管成本上综合最优（昆仑已选用），但需从单集合升级为多集合分域架构，并引入 BGE-M3 多向量（dense+sparse+colbert）混合检索。
3. **知识图谱**：Neo4j 原生图性能最强（昆仑已支持），但需扩展时序边（valid_from/valid_to）和社区检测（Leiden）以支持 GraphRAG 式全局查询。
4. **长期记忆**：Letta(MemGPT) 的 OS 式分页、Zep/Graphiti 的时序知识图谱、Cognee 的三存储混合架构最具借鉴价值；昆仑应建立"工作记忆→情景记忆→语义记忆→程序记忆"四层模型。
5. **RAG 高级技术**：HyDE + Query Rewriting + RRF 混合检索 + BGE-Reranker 重排序是召回率提升的黄金组合；GraphRAG 的社区摘要可解决"全书主题级"查询。
6. **专用数据结构**：角色状态卡（State Card）、情感弧光曲线、伏笔生命周期管理器是长篇一致性的三大支柱；昆仑 ontology 已有基础，需补充时序状态快照和情感维度。

**核心建议**：昆仑应在现有 kg/context/vibe_writer 之上新增 `kunlun/memory/` 模块，实现四层记忆架构，并将 Qdrant 从单集合扩展为 6 集合分域，将 Neo4j 图谱扩展为时序图 + 社区检测。

## 第一部分：长篇小说的上下文管理技术

### 1.1 Token 预算管理策略

#### 技术 1：滑动窗口 (Sliding Window)

- **链接**：https://github.com/pyonkichi369/ai-wikis/blob/main/concepts/llm-context-window.md
- **核心原理**：只保留最近 N 轮对话/章节，更早的直接丢弃。从最新消息向前累加 token，直到达到预算上限。
- **优点**：实现极简、延迟可预测、无额外 LLM 调用
- **缺点**：硬截断导致早期关键信息（如世界观设定、人物初始动机）永久丢失；"中间消失"问题（lost in the middle）
- **成熟度**：★★★★★（工业界标配）
- **昆仑可借鉴点**：昆仑 `context/budget.py` 的 `sliding_window_weight()` 已实现分段加权滑动窗口（1章=1.0, 5章=0.8, 10章=0.6, 20章=0.4），优于硬截断。建议增加"锚点保留"机制——世界观/主角卡等稳定内容不参与滑动。

#### 技术 2：渐进式摘要 (Progressive Summarization / Recursive Summarization)

- **链接**：https://arxiv.org/pdf/2308.15022v3 (Recursively Summarizing Enables Long-Term Dialogue Memory)
- **核心原理**：LLM 先对短对话生成摘要，然后递归地将"前摘要 + 新对话"合并更新为新摘要。MemoryBank 进一步引入艾宾浩斯遗忘曲线，按时间衰减记忆强度。
- **优点**：信息保留率高（10 条消息压缩为 200-400 token 仍保留 95%+ 语义）；无硬截断
- **缺点**：摘要本身可能引入幻觉；多次递归摘要后细节模糊；需要额外 LLM 调用成本
- **成熟度**：★★★★☆（学术验证充分，工业界广泛采用）
- **昆仑可借鉴点**：昆仑目前章节摘要为静态生成，建议改为"滚动摘要"——每写完 5 章，用 LLM 将"前 5 章摘要 + 新 5 章"合并为更新版摘要，形成 L0(单章)→L1(5章)→L2(20章)→L3(全书) 四级摘要树。这正是 RAPTOR 技术的小说化应用。

#### 技术 3：分层上下文 (Hierarchical Context)

- **链接**：https://www.aiplusinfo.com/blog/ai-agent-memory-architecture-explained/
- **核心原理**：将上下文分为工作记忆（当前任务）、情景记忆（具体事件）、语义记忆（持久事实）、程序记忆（如何做）四层，按查询类型动态加载不同层。
- **优点**：信息组织清晰；可按重要性差异化存储精度；支持跨会话持久化
- **缺点**：架构复杂；层间同步成本高；需要精准的写入/检索路由
- **成熟度**：★★★★☆（Cognee、Letta 等已实现）
- **昆仑可借鉴点**：昆仑现有 6 段预算本质是"平面分层"，建议升级为"立体分层"——6 段属于工作记忆层，新增情景记忆层（章节事件库）和语义记忆层（世界观/人物事实库），写作时按需从下层检索注入。

#### 技术 4：上下文压缩与主动遗忘 (Context Compression & Forgetting)

- **链接**：https://www.cambridge.org/engage/coe/article-details/6976210b5cdf9e3db45ef2b2 (Goldfish to Elephant)
- **核心原理**：当记忆容量超阈值时，通过学习型记忆门控网络（memory-gating network）选择性地将情景记忆压缩为语义表示；借鉴艾宾浩斯遗忘曲线，低访问频率、低重要性的记忆自然衰减。
- **优点**：记忆增长可控；重要信息优先保留；符合人类认知规律
- **缺点**：遗忘决策可能误删关键伏笔；需要训练门控网络或设计精细规则
- **成熟度**：★★★☆☆（学术前沿，工业界初步应用）
- **昆仑可借鉴点**：昆仑 `temporal_memory.py` 已有 `relevance_score` 和 `accessed_count` 字段，但未实现真正的遗忘。建议增加：(1) 伏笔/主线事件标记为"永不遗忘"；(2) 路人对话/过渡场景按访问频率自动归档为压缩摘要；(3) 每 50 章执行一次"记忆整理"，将低价值条目合并。

#### 技术 5：Lost in the Middle 缓解策略

- **链接**：https://zylos.ai/research/2026-01-19-llm-context-management/
- **核心原理**：研究表明 LLM 对上下文开头和结尾的信息注意力最强，中间信息容易被忽略。缓解策略包括：关键信息放置在首尾、重复重要约束、使用指令锚定（"请特别注意以下规则"）。
- **优点**：零成本提升信息利用率
- **缺点**：需要精心设计 prompt 结构
- **成熟度**：★★★★☆（广泛认知）
- **昆仑可借鉴点**：昆仑 6 段装配时，应将"系统规则"和"当前蓝图"放在 prompt 首尾，"历史摘要"放中间；对关键伏笔/人物状态使用重复锚定。

| character_cards | 18% | 角色/世界观卡片 | ✅ 已有 |
| dynamic_facts | 12% | 动态事实（真相关键点） | ✅ 已有 |
| chapter_summaries | 22% | 历史章节摘要 | ✅ 已有 |

**增强建议**：
1. 将 `chapter_summaries` 从"平面摘要列表"升级为"摘要树检索结果"——根据当前章节主题，从 L0/L1/L2 摘要中动态检索最相关的 3-5 条，而非简单取最近 N 章。
2. 新增 `foreshadowing_alerts` 子段（从 dynamic_facts 中拆分），专门注入"即将到期的伏笔提醒"。
3. `character_cards` 应区分"在场角色卡"（详细）和"提及角色卡"（极简），按场景动态选择。

## 第二部分：向量数据库在创作中的应用

### 2.1 向量数据库对比

#### 技术 6：Qdrant

- **链接**：https://qdrant.tech/
- **核心原理**：Rust 编写，HNSW 索引，支持 payload 过滤、标量量化（int8 节省 75% 内存）、稀疏-稠密混合检索。p50 延迟 ~4-8ms，p99 ~24ms（10M 向量规模）。
- **优点**：延迟最低、过滤精度高、自托管免费、内存优化好（量化+mmap）、Rust 性能稳定
- **缺点**：分布式集群需企业版；生态不如 Pinecone 成熟
- **成熟度**：★★★★★（生产级，昆仑已选用）
- **昆仑可借鉴点**：昆仑 `kg/client.py` 已启用 int8 标量量化和 HNSW(m=16, ef_construct=100)。建议：(1) 从单集合升级为多集合分域；(2) 启用 Qdrant 的稀疏向量（BM42）支持混合检索；(3) 利用 group_id 实现按书籍隔离。

#### 技术 7：Chroma

- **链接**：https://www.trychroma.com/
- **核心原理**：DuckDB 后端，嵌入式部署，默认 cosine 距离。p50 延迟 6.4ms（小规模），但 10M+ 向量后性能急剧下降。
- **优点**：零配置、嵌入式、Python 原生、开发体验极佳
- **缺点**：不适合大规模（>10M 向量不推荐）、过滤功能弱、无量化
- **成熟度**：★★★☆☆（原型/小规模）
- **昆仑可借鉴点**：不建议替换 Qdrant。可作为"轻量级测试模式"的备选——当用户未安装 Qdrant 时降级使用。

#### 技术 8：Milvus

- **链接**：https://milvus.io/
- **核心原理**：C++ 编写，分布式架构，支持 IVF/HNSW/ANNOY 多种索引。插入吞吐 38,500 vec/s，p50 4.1ms，p99 24.7ms。
- **优点**：大规模性能最强（亿级向量）、支持 GPU 加速、云原生
- **缺点**：部署复杂（依赖 etcd/MinIO/Pulsar）、资源消耗大、单机模式臃肿
- **成熟度**：★★★★★（超大规模生产级）
- **昆仑可借鉴点**：单机桌面版不需要 Milvus。若未来推出"云端多用户 SaaS 版"，可考虑用 Milvus 替换 Qdrant 支撑亿级向量。

#### 技术 9：Pinecone

- **链接**：https://www.pinecone.io/
- **核心原理**：全托管 Serverless 向量数据库，自动扩缩容。p50 6.4ms，p99 22.1ms，Filtered Recall@10 0.96。
- **优点**：零运维、Serverless 按用量付费、性能稳定、混合检索原生支持
- **缺点**：成本高（100M 向量 ~$650/月）、数据出境风险、无法自托管
- **成熟度**：★★★★★（企业级托管）
- **昆仑可借鉴点**：不适合桌面版。可作为"云端协作版"的可选后端。

#### 技术 10：Weaviate

- **链接**：https://weaviate.io/
- **核心原理**：Go 编写，支持 GraphQL 查询、模块化（向量化/重排内置）、混合检索。p50 ~48ms。
- **优点**：GraphQL 表达力强、内置向量化模块、多租户支持好
- **缺点**：延迟高于 Qdrant/Milvus、内存占用大
- **成熟度**：★★★★☆（生产级）
- **昆仑可借鉴点**：其"模块化内置 reranker"设计值得借鉴——昆仑可在 Qdrant 检索后自动串联 BGE-Reranker。

#### 技术 11：pgvector

- **链接**：https://github.com/pgvector/pgvector
- **核心原理**：PostgreSQL 扩展，HNSW/IVFFlat 索引。p50 9.1ms，p99 58.3ms，插入吞吐 12,400 vec/s。
- **优点**：与关系数据共存、事务一致性、无需额外运维、成本低（~$180/月）
- **缺点**：大规模性能不如专用向量库、过滤+向量联合查询优化有限
- **成熟度**：★★★★☆（中小规模生产级）
- **昆仑可借鉴点**：昆仑已有 SQLite 图降级模式，可参考 pgvector 思路——在 SQLite 中集成简单的向量检索（如 sqlite-vec）作为 Qdrant 不可用时的降级方案。

### 2.3 中文 Embedding 模型对比

#### 技术 12：BGE-M3 (BAAI)

- **链接**：https://huggingface.co/BAAI/bge-m3
- **核心原理**：568M 参数，支持 dense(1024维) + sparse(ColBERT) + multi-vector 三种输出，100+ 语言，8192 token 长上下文。MTEB 63.0，MLDR nDCG@10 65.0。
- **优点**：中文检索 SOTA、一次前向同时输出 dense+sparse（无需单独 BM25）、长文档支持好、ONNX int8 量化仅损失 ~1%
- **缺点**：模型较大（FP16 2.2GB，int8 558MB）、短文本延迟 28ms（高于轻量模型）
- **成熟度**：★★★★★（中文检索首选）
- **昆仑可借鉴点**：昆仑当前使用 768 维 BGE（`VectorParams(size=768)`），建议升级为 BGE-M3：(1) dense 维度升至 1024；(2) 利用其 sparse 输出实现混合检索，省去单独 BM25 索引；(3) 长章节摘要可直接编码（8192 token 支持）。

#### 技术 13：BGE-large-zh-v1.5

- **链接**：https://huggingface.co/BAAI/bge-large-zh-v1.5
- **核心原理**：326M 参数，1024 维，中文专用，512 token。MTEB 中文榜长期领先。
- **优点**：中文短文本检索精准、模型适中（1.3GB）、社区生态成熟
- **缺点**：仅中文、不支持稀疏向量、上下文短（512 token）
- **成熟度**：★★★★★
- **昆仑可借鉴点**：作为 BGE-M3 的轻量备选——资源受限的桌面版可使用此模型。

#### 技术 14：M3E (Moka)

- **链接**：https://github.com/wangyh070/M3E
- **核心原理**：基于 Roberta，中文问答场景优化。M3E-base 768 维，M3E-large 1024 维。中文问答召回率比通用模型高 18%。
- **优点**：中文问答场景强、边缘部署友好（内存占用低）、训练数据包含大量中文问答对
- **缺点**：通用语义检索不如 BGE-M3、长文本支持弱、社区维护放缓
- **成熟度**：★★★☆☆
- **昆仑可借鉴点**：其"问答对训练"思路可用于微调——用小说中的"情节查询→相关段落"对微调 BGE-M3，提升情节检索精度。

#### 技术 15：text2vec (Shibing624)

- **链接**：https://github.com/shibing624/text2vec
- **核心原理**：基于 CoSENT 损失的中文句向量框架，支持多种基座（BERT/ERNIE/MacBERT）。
- **优点**：框架灵活可自定义基座、训练代码完整、中文匹配任务表现好
- **缺点**：需要自行训练/选择基座、预训练模型质量参差不齐
- **成熟度**：★★★☆☆
- **昆仑可借鉴点**：参考其 CoSENT 训练方法，用于领域微调。

#### 技术 16：GTE (Alibaba)

- **链接**：https://huggingface.co/thenlper/gte-large
- **核心原理**：阿里巴巴通用文本嵌入，GTE-Large 1024 维，多语言支持。
- **优点**：多语言均衡、短文本检索稳定、推理速度快
- **缺点**：中文长文本不如 BGE-M3、不支持稀疏向量
- **成熟度**：★★★★☆
- **昆仑可借鉴点**：作为多语言场景备选。

| 用途 | 查询示例 | 检索目标 | 昆仑现状 |
|------|----------|----------|----------|
| 相似情节检索 | "主角被背叛后隐忍复仇的情节" | 历史章节段落 | ✅ `index_chapter_vector` |
| 人物对话风格检索 | "高冷女主的说话方式" | 角色对话段落 | ❌ 需新增角色对话集合 |
| 世界观规则检索 | "修炼突破时的天劫规则" | 世界观设定段落 | ❌ 需新增世界观集合 |
| 伏笔线索检索 | "与玉佩相关的所有线索" | 伏笔+相关段落 | ❌ 需图谱+向量联合 |
| 场景描写检索 | "雨夜战斗的氛围描写" | 环境描写段落 | ❌ 需按描写类型分域 |

### 2.6 向量检索召回率优化策略

1. **混合检索 (Hybrid Search)**：dense 向量 + sparse(BM25/BM42) + RRF(Reciprocal Rank Fusion) 融合。研究表明 RRF+Reranker 是全局最优组合，pool=50 是最优平衡点。
2. **查询改写 (Query Rewriting)**：用 LLM 将自然语言查询改写为 3-5 个语义变体，分别检索后合并。
3. **HyDE**：先用 LLM 生成"假设性答案段落"，再用该段落的向量检索（详见第五部分）。
4. **重排序 (Reranking)**：初检取 top-50，用 BGE-Reranker-v2-m3 交叉编码器重排序，取 top-5/10。
5. **分域检索**：按内容类型分集合（情节/对话/世界观/描写），查询时先判断类型再定向检索，避免跨域噪声。
6. **元数据过滤**：利用 Qdrant payload 过滤（book_id、chapter_range、character_id），先缩小候选集再向量排序。
7. **距离衰减重排**：昆仑已实现 `vector_search_with_decay()`，语义相似度 × 章节距离对数衰减权重。

## 第三部分：知识图谱在创作中的应用

### 3.1 图数据库对比

#### 技术 17：Neo4j

- **链接**：https://neo4j.com/
- **核心原理**：原生属性图数据库（Property Graph），节点+关系+属性，Cypher 查询语言。免索引邻接（index-free adjacency），每个节点直接指向邻居，遍历复杂度与图规模无关。异步驱动 + Rust 扩展可获 3-10x 性能提升。
- **优点**：图查询性能最强（复杂遍历 MySQL 呈指数增长，Neo4j 保持稳定）、Cypher 表达力强、生态成熟（APOC/GDS 库）、社区版免费
- **缺点**：企业版收费（集群/高可用）、内存占用大、写入吞吐量不如关系型
- **成熟度**：★★★★★（图数据库事实标准）
- **昆仑可借鉴点**：昆仑 `kg/client.py` 已支持 Neo4j + SQLite 图降级双模式，已创建 9 类实体约束和 8 个索引。建议：(1) 扩展时序边属性（valid_from_chapter / valid_to_chapter）；(2) 集成 Neo4j GDS 库的 Leiden 社区检测算法；(3) 增加 APOC 路径查询用于多跳推理。

#### 技术 18：NetworkX

- **链接**：https://networkx.org/
- **核心原理**：纯 Python 图分析库，内存中图结构，支持 30+ 图算法（中心性/社区检测/最短路径）。
- **优点**：零依赖、API 简洁、算法丰富、适合原型验证和小规模分析
- **缺点**：纯内存（>10万节点性能急剧下降）、无持久化、无查询语言、单机单线程
- **成熟度**：★★★★☆（学术/原型标准）
- **昆仑可借鉴点**：可用于"离线图谱分析"——将 Neo4j 数据导出为 NetworkX 图，运行社区检测/中心性分析后将结果写回 Neo4j。不适合作为主存储。

#### 技术 19：Apache AGE

- **链接**：https://age.apache.org/
- **核心原理**：PostgreSQL 扩展，在关系数据库中实现属性图，支持 openCypher 查询。图数据存储为 PG 行，查询时图原生遍历。
- **优点**：与关系数据共存（事务一致性）、利用 PG 生态（备份/监控/扩展）、openCypher 兼容、无需单独运维图数据库
- **缺点**：图查询性能不如 Neo4j（复杂遍历有 overhead）、社区较小、PG 19 将引入 SQL/PGQ 标准可能替代
- **成熟度**：★★★☆☆
- **昆仑可借鉴点**：若未来昆仑从 SQLite 迁移到 PostgreSQL，可考虑用 AGE 替代 SQLite 图降级模式，获得更强的图查询能力。

#### 技术 20：Memgraph

- **链接**：https://memgraph.com/
- **核心原理**：C++ 编写的内存原生图数据库，兼容 Cypher，支持流式图计算（streaming graph algorithms）。
- **优点**：内存级性能（比 Neo4j 快 2-10x）、Cypher 兼容、内置图算法、支持 Kafka 流
- **缺点**：生态不如 Neo4j、企业版收费、社区活跃度中等
- **成熟度**：★★★☆☆
- **昆仑可借鉴点**：其"流式图计算"理念可借鉴——章节写入时实时更新人物关系/情感变化，而非批量离线计算。

#### 技术 21：Kuzu

- **链接**：https://kuzudb.com/
- **核心原理**：嵌入式图数据库（类似 SQLite 的图版），C++ 编写，支持 Cypher，列式存储。
- **优点**：嵌入式零运维、列式存储压缩率高、查询性能优秀、支持大规模图
- **缺点**：项目较新、生态不成熟、客户端语言支持有限
- **成熟度**：★★☆☆☆
- **昆仑可借鉴点**：长期可考虑用 Kuzu 替代 SQLite 图降级模式，获得嵌入式原生图查询能力。

### 3.3 知识图谱在创作中的具体应用

#### 人物关系图谱

- **构建方式**：从章节文本中抽取人物实体和关系（KNOWS/TRUSTS/HOSTILE/IN_LOVE_WITH/MASTER_OF 等），昆仑 ontology 已定义 11 类人物关系。
- **查询模式**：
  - "主角和谁的信任度最高？" → 匹配 TRUSTS 边按权重排序
  - "找出所有与主角敌对的角色及其盟友" → 2 跳遍历 HOSTILE→KNOWS
  - "角色A和角色B之间有哪些间接关系？" → 最短路径查询
- **昆仑增强**：当前关系边缺少时序属性，建议增加 `valid_from_chapter` 和 `valid_to_chapter`，支持"第50章时谁是主角的盟友"这类时序查询。

#### 世界观图谱

- **实体类型**：Location（地点）、Organization（势力）、Item（物品）、Skill（技能）、Knowledge（世界观知识）
- **关系类型**：PARENT_OF（地点层级）、HOSTILE_ORG（势力敌对）、POSSESSES（物品归属）、EVOLUTION_OF（技能演化）
- **查询模式**：
  - "天玄宗的敌对势力有哪些？各自控制哪些地点？" → 组织→地点多跳查询
  - "这把剑之前被谁拥有过？" → Item 的 owner_history 时序查询
- **昆仑增强**：当前 Location 有 parent_location_uid，但未在图谱中建立 PARENT_OF 边；建议将层级关系显式化为图边，支持"某地点所属的所有上级区域"查询。

#### 伏笔/真相图谱

- **实体类型**：Foreshadowing（伏笔）、Event（事件）、Truth（真相）
- **关系类型**：PLANTED_FOR（伏笔为谁埋设）、REVEALED_BY（伏笔由何事件揭示）、RELATED_TO（线索关联）
- **查询模式**：
  - "找出所有状态为 planted 且 expected_reveal_chapter < 当前章的伏笔" → 逾期伏笔预警
  - "与'玉佩之谜'相关的所有伏笔和线索" → 以伏笔为中心的子图展开
  - "某真相涉及哪些角色？分别在哪些章节获得了线索？" → 多跳时序查询
- **昆仑增强**：ontology 已有 Foreshadowing 实体（planted_chapter/status/priority/expected_reveal_chapter），但缺少与 Event/Character 的显式图边。建议增加 PLANTED_FOR 和 REVEALED_BY 边的自动构建。

#### 时间线管理

- **核心挑战**：事件的先后顺序、因果关系、时间重叠检测
- **图谱建模**：Event 节点带 `chapter_range` 和 `timestamp`，事件间用 CAUSES（因果）、PRECEDES（先后）、OVERLAPS（重叠）边连接
- **查询模式**：
  - "主角从离开宗门到到达帝都之间发生了哪些事件？" → 时间范围过滤 + 事件链遍历
  - "事件A和事件B是否存在因果关系？中间经过哪些事件？" → 因果链路径查询
  - "检测时间线矛盾：角色A在第30章死亡但在第50章出现" → 时序一致性校验
- **昆仑增强**：当前 Event 有 chapter_range 但无事件间关系边。建议增加 CAUSES/PRECEDES 边，并在审计模块中增加时间线一致性检查。

### 3.4 图谱的自动构建技术

#### 技术 22：LLM 实体关系抽取 (GraphRAG 式)

- **链接**：https://arxiv.org/pdf/2404.16130.pdf (Microsoft GraphRAG)
- **核心原理**：将文本切分为 TextUnit，用 LLM 从每个 TextUnit 中抽取实体、关系和关键声明（claims），构建文档级知识图谱。使用 Leiden 算法进行层次化社区检测，为每个社区生成摘要。
- **优点**：自动化程度高、可处理非结构化文本、社区摘要支持全局查询
- **缺点**：LLM 抽取成本高（每章需多次 LLM 调用）、抽取质量依赖 prompt 设计、存在幻觉风险
- **成熟度**：★★★★☆（微软开源，工业界快速采用）
- **昆仑可借鉴点**：昆仑可在每章写完后，用 LLM 抽取该章的实体/关系增量更新图谱。关键优化：(1) 只抽取"新实体"和"关系变化"，避免重复；(2) 用昆仑已有的 ontology 约束抽取类型，减少幻觉；(3) 批量处理（每 5 章抽取一次）降低成本。

#### 技术 23：基于规则的实体链接

- **核心原理**：利用 jieba 分词 + 人名词典 + 别名映射，从文本中识别已知实体的出现位置，更新其 last_modified_chapter。
- **优点**：零 LLM 成本、速度快、确定性高
- **缺点**：无法发现新实体/新关系、对别名/代称处理有限
- **成熟度**：★★★★★
- **昆仑可借鉴点**：作为 LLM 抽取的前置/补充——先用规则快速更新已知实体的出现信息，再用 LLM 抽取新关系。

#### 技术 24：增量式图谱更新

- **核心原理**：每章写入时，只更新受影响的子图（当前场景的角色/地点/物品），而非全图重建。使用"脏标记"（dirty flag）标记需要重新计算的节点。
- **优点**：写入性能好、适合流式创作
- **缺点**：全局指标（如社区划分）需要定期重算
- **昆仑可借鉴点**：昆仑当前 `index_chapter_vector` 是增量式的，但图谱更新缺少增量机制。建议为 KGClient 增加 `update_from_chapter(chapter_text, chapter_num)` 方法，增量抽取并更新。

## 第四部分：长期记忆架构项目

### 4.1 主流长期记忆框架

#### 技术 25：Letta (原 MemGPT)

- **链接**：https://letta.com/ | https://github.com/letta-ai/letta
- **核心原理**：受操作系统虚拟内存管理启发，将 LLM 上下文视为"RAM"，外部存储视为"磁盘"。三层记忆架构：
  - **Core Memory（核心记忆）**：始终在上下文窗口内，由可编辑的 memory block 组成（persona/human 等），Agent 通过工具调用自主编辑
  - **Recall Memory（回忆记忆）**：完整对话历史，按需检索（搜索式）
  - **Archival Memory（档案记忆）**：长期知识存储，向量数据库，Agent 通过 `archival_memory_insert/search` 工具自主管理
- **优点**：OS 式分页设计优雅、Agent 自主管理记忆（self-editing）、支持跨会话持久化、LongMemEval 83.2%
- **缺点**：记忆管理消耗 token（工具调用开销）、Core Memory 容量有限、需要 Agent 学会何时写入/检索
- **成熟度**：★★★★☆（~23K stars，生产可用）
- **昆仑可借鉴点**：
  1. **Core Memory 理念** → 昆仑的 6 段上下文中，system_rules + character_cards + current_blueprint 可视为"Core Memory"，始终驻留
  2. **Archival Memory 工具化** → 为写作 Agent 增加 `memory_search(query)` 和 `memory_save(fact)` 工具，让 Agent 自主决定何时检索/保存
  3. **自主编辑机制** → 角色卡不是静态的，Agent 可在写作过程中通过工具更新角色状态

#### 技术 26：Zep / Graphiti

- **链接**：https://www.getzep.com/ | https://github.com/getzep/graphiti
- **核心原理**：时序知识图谱（Temporal Knowledge Graph）引擎。三层架构：
  - **Episode Subgraph（情节子图）**：原始消息/文本/JSON 的非损失存储，双时序模型（event timeline + transaction timeline）
  - **Semantic Entity Subgraph（语义实体子图）**：从对话中抽取的实体及其关系，带有效时间区间（valid_at/expired_at）
  - **事实合成层**：动态合成对话数据和结构化业务数据，支持时序推理
- **优点**：时序推理能力最强（"3个月前用户对X的看法是什么？"）、实体关系自动抽取、Sub-200ms 查询延迟、LongMemEval 63.8%
- **缺点**：图数据库运维开销大、抽取质量依赖 LLM、企业级定价
- **成熟度**：★★★★☆（~24K stars，企业级）
- **昆仑可借鉴点**：
  1. **时序图建模** → 昆仑图谱的所有关系边应增加 `valid_from_chapter` / `valid_to_chapter`，支持"第N章时的人物关系"查询
  2. **Episode + Semantic 双层** → 昆仑可区分"原始章节文本"（Episode，非损失存储）和"抽取的实体关系"（Semantic，结构化）
  3. **双时序模型** → 区分"故事内时间"（小说世界的时间线）和"写作时间"（作者创作的章节顺序）

#### 技术 27：Mem0

- **链接**：https://mem0.ai/ | https://github.com/mem0ai/mem0
- **核心原理**：混合存储架构（Vector + Graph + KV），自动从对话中提取结构化记忆（事实/偏好/事件），支持记忆的添加/搜索/更新/删除。记忆带 metadata（user_id/agent_id/session_id）和层级（user-level/agent-level/session-level）。
- **优点**：接入简单（一行代码）、自动提取结构化记忆、支持多用户隔离、记忆更新自动去重、~48K stars
- **缺点**：Pro 版才支持图记忆（$249/月）、记忆质量依赖输入信号、不适合复杂图查询
- **成熟度**：★★★★★（最流行的开源记忆框架）
- **昆仑可借鉴点**：
  1. **自动记忆提取** → 每章写完后，用 LLM 自动提取"本章新增事实"（角色状态变化/新关系/新伏笔），结构化存入记忆库
  2. **记忆层级** → 区分 book-level（全书设定）、arc-level（故事线）、chapter-level（单章事件）三级记忆
  3. **自动去重/更新** → 新事实与已有事实冲突时，自动标记为"更新"而非"新增"

#### 技术 28：LangChain Memory / LangMem

- **链接**：https://python.langchain.com/docs/concepts/memory/
- **核心原理**：提供记忆原语（building blocks）而非完整系统。包括 ConversationBufferMemory（全量缓冲）、ConversationSummaryMemory（摘要）、ConversationKGMemory（知识图谱）、VectorStoreRetrieverMemory（向量检索）。LangMem 进一步引入 3 类认知记忆（semantic/episodic/procedural）× 2 种范围（short/long-term）× 2 种机制（hot path/background）。
- **优点**：灵活可组合、与 LangChain 生态深度集成、原语丰富
- **缺点**：是"积木"不是"系统"——需要自行设计提取逻辑/存储 schema/检索策略、Checkpointer ≠ Memory（仅用于崩溃恢复）
- **成熟度**：★★★★☆（生态标准）
- **昆仑可借鉴点**：其"3×2×2"认知记忆分类法可作为昆仑记忆分层的理论框架。昆仑已有 VectorStoreRetrieverMemory 式的向量检索，可补充 KGMemory 式的图谱记忆。

#### 技术 29：LlamaIndex Memory

- **链接**：https://docs.llamaindex.ai/en/stable/module_guides/deploying/agents/memory/
- **核心原理**：可组合记忆缓冲区（Composable Memory Buffers），支持短期记忆（FIFO 缓冲）和长期记忆（向量检索 + 事实提取）。`extracted_info` 模块从刷新的聊天历史中提取事实，超过 max_facts 时触发压缩。
- **优点**：与 LlamaIndex 索引/检索深度集成、可组合性强、支持自定义记忆类型
- **缺点**：绑定 LlamaIndex 生态、长期记忆功能相对基础
- **成熟度**：★★★☆☆
- **昆仑可借鉴点**：其"事实提取 + 容量触发压缩"机制可借鉴——当角色卡/世界观卡超过 token 预算时，自动压缩为摘要。

#### 技术 30：Cognee

- **链接**：https://www.cognee.ai/ | https://github.com/topoteretes/cognee
- **核心原理**：三存储混合架构（relational + vector + graph），认知科学启发的三层记忆：
  - **Semantic Memory（语义记忆）**：事实/概念/知识图谱
  - **Episodic Memory（情景记忆）**：过去对话/交互记录
  - **Procedural Memory（程序记忆）**：任务执行模式/工作流
  - Session Memory（短期工作记忆）加载相关嵌入和图片段到运行时；Permanent Memory（永久记忆）存储长期知识。图和向量存储保持链接——每个图节点有对应嵌入。
- **优点**：三存储覆盖最全面、图+向量联动、自动生成领域本体、~18K stars
- **缺点**：架构复杂、运维成本高、记忆提取延迟
- **成熟度**：★★★☆☆
- **昆仑可借鉴点**：
  1. **三存储架构** → 昆仑已有 Qdrant（向量）+ Neo4j/SQLite（图），可补充关系型存储（结构化事实表）
  2. **图节点嵌入联动** → 昆仑可在创建图谱节点时自动生成其文本描述的向量，实现"图遍历→向量检索"无缝切换
  3. **Procedural Memory** → 昆仑可增加"写作模式记忆"——记录某类场景（战斗/对话/突破）的成功写作模板

#### 技术 31：Supermemory

- **链接**：https://supermemory.ai/
- **核心原理**：Memory + RAG + 用户画像 + 连接器 + 提取器一体化平台。核心创新是"Dynamic Dreaming"（动态做梦）——在后台自动整理、合并、提炼记忆，类似人类睡眠时的记忆巩固过程。使用自定义图引擎构建知识图谱。
- **优点**：一体化程度高、Dynamic Dreaming 自动记忆整理、极低延迟、支持多数据源连接器
- **缺点**：闭源为主、自托管仅企业版、定价较高
- **成熟度**：★★★☆☆
- **昆仑可借鉴点**：**Dynamic Dreaming 理念** → 昆仑可在后台守护进程（daemon.py）中增加"记忆整理"任务：每写完 N 章后，自动合并相似伏笔、更新角色关系摘要、压缩过时情景记忆。

#### 技术 32：MemoryBank

- **链接**：https://arxiv.org/pdf/2308.15022v3 (MemoryBank 论文)
- **核心原理**：类人长期记忆机制，创建带时间戳的有序对话摘要，重新组织为全局记忆。记忆遵循艾宾浩斯遗忘曲线——随时间自然衰减，重要记忆通过"复习"（retrieval）得到巩固。
- **优点**：符合人类认知规律、遗忘机制自然、记忆增长可控
- **缺点**：遗忘可能误删关键信息、需要设计重要性评分
- **成熟度**：★★★☆☆（学术原型）
- **昆仑可借鉴点**：其艾宾浩斯遗忘曲线可用于昆仑的"情景记忆衰减"——章节事件记忆随章节距离自然衰减，但被检索到的记忆得到"巩固"（衰减速度减慢）。

## 第五部分：RAG 在创作中的高级应用

### 5.1 核心 RAG 增强技术

#### 技术 33：HyDE（Hypothetical Document Embeddings）

- **链接**：https://arxiv.org/abs/2212.10496 | https://ai-tldr.dev/learn/rag/retrieval-and-reranking/what-is-hyde-rag/
- **核心原理**：不直接用查询文本做向量检索，而是先用 LLM 生成一个"假设性答案段落"（即使内容是虚构的），然后用这个假设性段落的向量去检索。因为假设性答案在语义空间中更接近真实文档（查询和文档处于不同语义邻域，HyDE 桥接了这个 gap）。
- **优点**：零样本场景下显著提升召回率、对模糊/抽象查询效果尤佳、无需训练数据
- **缺点**：增加一次 LLM 调用（延迟+成本）、假设性答案可能带偏检索方向（尤其当 LLM 对领域不熟悉时）、对简单精确查询可能反而降低效果
- **成熟度**：★★★★☆（广泛验证，工业界常用）
- **昆仑可借鉴点**：
  - **适用场景**：当用户说"写一段主角突破时的感悟"时，先用 LLM 生成一段假设性的"突破感悟"文本，再用它去向量库中检索过往类似的突破描写，而非直接用"突破感悟"4个字检索。
  - **实现位置**：在 `kg/client.py` 的 `vector_search()` 前增加可选的 `use_hyde=True` 参数，对创作类查询自动启用。
  - **成本控制**：仅对查询长度 < 20 字的模糊查询启用 HyDE，对明确的实体查询（"主角的玉佩"）跳过。

#### 技术 34：Query Rewriting（查询改写）

- **链接**：https://www.callsphere.ai/blog/advanced-rag-patterns-query-rewriting-hyde-multi-step-retrieval
- **核心原理**：用 LLM 将原始查询改写为 3-5 个语义变体（包括关键词扩展、同义词替换、视角转换），分别检索后合并去重。也包括"子查询分解"——将复杂查询拆为多个简单子查询分别检索。
- **优点**：提升召回率（多视角覆盖）、对口语化/模糊查询效果好、可与 HyDE 叠加
- **缺点**：检索次数翻倍（延迟+成本）、结果合并需要去重逻辑、改写质量依赖 LLM
- **成熟度**：★★★★★（工业界标配）
- **昆仑可借鉴点**：
  - **小说场景适配**：用户说"让这段更有张力"→ 改写为 ["增加冲突强度", "提升情感紧张感", "加快节奏", "增加悬念"] 4 个变体，分别检索过往"高张力"场景。
  - **实现方式**：在 vibe_writer 的写作流程中，对用户的 Vibe 指令先做查询改写，再从记忆库检索参考素材。

#### 技术 35：Multi-hop RAG（多跳推理检索）

- **链接**：https://arxiv.org/abs/2310.03714 (MuSiQue) | https://ai-tldr.dev/learn/rag/advanced-rag/what-is-graphrag/
- **核心原理**：复杂问题需要跨越多个文档/实体进行推理。两种实现路径：(1) 迭代式检索——先检索回答子问题1，用其结果增强查询再检索子问题2；(2) 图遍历式——在知识图谱上做多跳遍历，收集路径上的所有实体和关系。
- **优点**：能回答"找出所有与主角复仇相关的伏笔"这类需要跨实体关联的复杂问题
- **缺点**：延迟高（多次检索/遍历）、错误会沿路径累积、需要复杂的推理编排
- **成熟度**：★★★☆☆（学术活跃，工业界初步应用）
- **昆仑可借鉴点**：
  - **小说场景**："主角的身世之谜涉及哪些伏笔？分别埋在哪些章节？" → 需要从 Character 节点出发，遍历 FORESHADOWING→EVENT→CHAPTER 多跳路径。
  - **实现方式**：利用 Neo4j 的 Cypher 多跳查询（`MATCH (c:Character)-[:PLANTED_FOR]->(f:Foreshadowing)-[:REVEALED_BY]->(e:Event)`），比迭代式向量检索更高效。

#### 技术 36：Reranking（重排序）

- **链接**：https://bge-model.com/bge/bge_reranker.html | https://ai-tldr.dev/learn/rag/retrieval-and-reranking/bge-reranker-cross-encoder/
- **核心原理**：先用双编码器（Bi-Encoder，即 Embedding 模型）快速检索 top-50/100 候选，再用交叉编码器（Cross-Encoder，即 Reranker）对每个(查询, 文档)对做精细打分排序，取 top-5/10。交叉编码器将查询和文档拼接后一起输入，能捕捉深层语义交互。
- **主流模型**：BGE-Reranker-v2-m3（多语言，中文优化）、BGE-Reranker-large（中文 SOTA）、Cohere Rerank 3.5（商业）
- **优点**：显著提升精确率（NDCG@10 提升 10-20%）、对中文语义匹配效果好、与混合检索叠加效果最佳
- **缺点**：增加计算开销（top-50 重排约 200-500ms）、需要额外模型部署、对 top-10 以外的结果无影响
- **成熟度**：★★★★★（工业界标配）
- **昆仑可借鉴点**：
  - **模型选择**：BGE-Reranker-v2-m3（与 BGE-M3 嵌入配套，多语言支持，中文优化）
  - **实现位置**：在 `vector_search_with_decay()` 的结果返回前，增加 rerank 步骤——初检取 top-30，重排后取 top-10。
  - **性能优化**：仅对相似度 > 0.5 的候选启动重排；pool=50 是最优平衡点（pool=20 漏候选，pool=100 无额外收益但延迟翻倍）。

#### 技术 37：自适应 RAG（Adaptive RAG）

- **链接**：https://arxiv.org/abs/2403.14403 (Adaptive-RAG)
- **核心原理**：根据查询的复杂度自动选择检索策略。简单事实型查询 → 直接向量检索；复杂推理型查询 → 多跳检索/图遍历；模糊主题型查询 → HyDE + 查询改写。用分类器（或 LLM 判断）先确定查询类型，再路由到对应策略。
- **优点**：在效果和成本间取得最优平衡、避免对简单查询过度工程化
- **缺点**：分类器本身可能误判、策略路由增加系统复杂度
- **成熟度**：★★★☆☆（学术前沿，工业界初步探索）
- **昆仑可借鉴点**：
  - **小说查询分类**：
    - 实体查询（"主角的修为"）→ 直接图谱查询
    - 情节查询（"类似的逆袭情节"）→ 向量检索 + 重排
    - 关联查询（"与玉佩相关的所有线索"）→ 图谱多跳遍历
    - 创作查询（"写一段高张力对话"）→ HyDE + 向量检索 + 风格匹配
  - **实现方式**：在记忆检索接口前增加查询分类器，用 LLM 或规则判断查询类型。

#### 技术 38：GraphRAG（微软）

- **链接**：https://arxiv.org/pdf/2404.16130.pdf | https://microsoft.github.io/graphrag/
- **核心原理**：两阶段架构：
  - **索引阶段**：LLM 从文本中抽取实体/关系/声明构建知识图谱 → Leiden 社区检测做层次化聚类 → 为每个社区（从底层到顶层）生成自然语言摘要
  - **查询阶段**：
    - Local Search：实体查找 + 图展开，回答具体实体问题
    - Global Search：社区摘要聚合，回答全书主题级问题（"这本书的主题是什么？"）
    - DRIFT Search：混合模式，从全局开始逐步聚焦到局部
- **优点**：能回答传统 RAG 无法处理的"全局/主题级"问题、社区摘要提供多分辨率视图、对长篇文档效果显著
- **缺点**：索引阶段计算成本极高（每章多次 LLM 调用）、社区检测质量依赖图质量、查询延迟较高
- **成熟度**：★★★★☆（微软开源，快速成熟）
- **昆仑可借鉴点**：
  - **社区摘要用于大纲生成**：每写完 20 章，对图谱做 Leiden 社区检测，为每个"故事线社区"生成摘要，自动汇总为卷大纲。
  - **Global Search 用于全书回顾**：完本时，用 Global Search 聚合所有社区摘要，生成全书主题分析和人物弧光总结。
  - **成本优化**：不需要每章都做全量抽取，可每 10 章做一次增量社区更新。

#### 技术 39：RAPTOR（递归抽象处理树组织检索）

- **链接**：https://arxiv.org/pdf/2401.18059.pdf | https://github.com/parthsarthi03/RAPTOR
- **核心原理**：自底向上构建摘要树——
  - L0：原始文本块
  - L1：对 L0 块做聚类（UMAP + GMM），每个聚类生成摘要
  - L2：对 L1 摘要再聚类再摘要
  - 直到根节点
  - 查询时同时从所有层级检索（Tree Traversal 或 Collapsed Tree），整合不同抽象级别的信息
- **优点**：同时保留细节（L0）和全局上下文（高层摘要）、对多跳推理和长文档问答效果显著提升
- **缺点**：构建树需要多次聚类+摘要 LLM 调用、树更新成本高（新文本需要重新聚类）、聚类参数敏感
- **成熟度**：★★★★☆（ICLR 2024，工业界快速采用）
- **昆仑可借鉴点**：
  - **章节摘要树**：昆仑可构建 L0(单章摘要) → L1(5章卷摘要) → L2(20章部摘要) → L3(全书摘要) 四级树。
  - **检索时多级别融合**：写新章时，同时从 L0（最近3章细节）、L1（当前卷主题）、L2（全书走向）检索，注入不同上下文段。
  - **增量更新**：新章写入时，只更新其所属 L1 节点的摘要，不重建整棵树。

#### 技术 40：混合检索 + RRF（Reciprocal Rank Fusion）

- **链接**：https://ai-tldr.dev/learn/rag/retrieval-and-reranking/bge-reranker-cross-encoder/
- **核心原理**：同时执行 dense 向量检索和 sparse 关键词检索（BM25/BM42），用 RRF 公式融合两个排名：`score(d) = Σ 1/(k + rank_i(d))`（k 通常=60）。RRF 不需要两个检索器的分数在同一尺度，鲁棒性强。
- **优点**：结合语义匹配（dense）和精确匹配（sparse）的优势、对专有名词/术语/数字查询效果显著提升、RRF 融合无需分数归一化
- **缺点**：需要维护两套索引、检索延迟翻倍、纯 RRF 不如 RRF+Reranker
- **成熟度**：★★★★★（工业界标配）
- **昆仑可借鉴点**：
  - **BGE-M3 一体化**：BGE-M3 可同时输出 dense 和 sparse(ColBERT) 向量，无需单独维护 BM25 索引。
  - **小说场景**：查询"萧炎第30章使用的斗技"——dense 检索找到语义相似的战斗描写，sparse 检索精确匹配"萧炎"/"斗技"/"30章"，融合后效果远优于单一检索。
  - **实现方式**：Qdrant 原生支持 sparse-dense 混合检索，升级 Qdrant 集合并启用 sparse 向量即可。

### 5.2 RAG 技术在小说创作中的应用矩阵

| 创作需求 | 推荐技术组合 | 预期效果 |
|----------|-------------|----------|
| 检索类似情节 | 向量检索 + Reranker + 距离衰减 | 召回相似桥段，避免重复 |
| 检索人物对话风格 | 分域向量检索(对话集合) + Reranker | 保持角色语言一致性 |
| 检索世界观规则 | 混合检索(dense+sparse) + 图谱过滤 | 确保不违反设定 |
| 全局主题回顾 | GraphRAG Global Search | 全书主题/人物弧光分析 |

| 创作灵感检索 | HyDE + 查询改写 + 向量检索 | 从模糊意图找到参考素材 |
| 章节上下文装配 | RAPTOR 摘要树 + 6段预算 | 多级别上下文融合 |
| 逾期伏笔预警 | 图谱过滤查询 + 元数据排序 | 自动提醒未回收伏笔 |

## 第六部分：角色记忆/情感弧光/伏笔管理的专用数据结构

### 6.1 角色状态追踪（Character State Card）

#### 技术 41：NovelOS Character Database

- **链接**：https://github.com/perry121108-dotcom/NovelOS_
- **核心原理**：标准化角色卡格式，包含人格/欲望/恐惧/成长弧光/能力体系/关系网络。角色卡不是静态的，每章后更新"当前状态"。
- **昆仑可借鉴点**：昆仑 ontology 的 Character 已有 personality_vector(12维)、arc_stage、current_realm 等字段，但缺少"当前状态快照"。

#### 技术 42：AI Story Studio State Card

- **链接**：https://aistorystudio.aibody.art/article/how-to-keep-long-ai-stories-consistent
- **核心原理**：区分"静态档案"（profile，角色初始设定）和"状态卡"（state card，角色当前状态）。状态卡在重要场景后更新，包含：当前目标、当前情绪、伤病/限制、位置、持有物、关系、新知识、承诺/义务、当前策略。
- **优点**：静态/动态分离避免设定被污染、状态卡紧凑可注入上下文、更新时机明确
- **昆仑可借鉴点**：昆仑应将 Character 实体拆分为"角色档案"（静态，ontology 定义）和"角色状态快照"（动态，每章或每重要场景更新）。

#### 技术 43：Novarrium Logic-Locking System

- **链接**：https://novarrium.com/blog/ai-romance-novel-writing-character-relationships
- **核心原理**：将角色关系作为"被追踪的事实"（tracked fact）存储，随剧情推进更新。例如"Elena和Marcus——互相吸引，未承认。Elena知道自己的感受但否认。Marcus无意识。"每条关系状态带时间戳和章节标记。
- **昆仑可借鉴点**：昆仑图谱的关系边应增加"关系状态描述"属性，而非仅有权重。例如 TRUSTS 边不仅有 trust_level=0.7，还有 status_description="表面合作，暗中提防"。

### 6.2 情感弧光管理（Emotional Arc）

#### 技术 44：Dramatica-Flow Emotional Arcs

- **链接**：https://github.com/Decentralised-AI/dramatica-flow-enhanced-v4
- **核心原理**：基于 Dramatica 叙事理论，每个角色有 1-10 强度的情感追踪。情感弧光引擎记录角色在每个关键节点的情绪状态，形成情感曲线。支持"情感矛盾"（角色内心冲突）和"关系情感"（角色间情感动态）。
- **昆仑可借鉴点**：昆仑 Character 的 personality_vector 是静态人格，应增加"情感状态时序序列"——记录每个关键章节的情绪标签和强度，形成可查询的情感曲线。

#### 技术 45：ESG（Emotional Semantic Generation）框架

- **链接**：https://dl.acm.org/doi/10.1145/3797161.3797162
- **核心原理**：数学化情感表示 + 双块结构（dual-block），为 Transformer 赋予长程情感伏笔和隐喻共鸣能力。将情感编码为可计算的向量，在生成过程中保持情感连贯性。
- **优点**：从架构层面解决情感一致性、支持长程情感伏笔
- **缺点**：需要修改模型架构、不适合即插即用
- **昆仑可借鉴点**：其"数学化情感表示"理念可借鉴——昆仑可用情感向量（如 Valence-Arousal-Dominance 三维）量化角色情绪，在上下文注入时保持情感趋势的连续性。

### 6.3 伏笔管理（Foreshadowing Manager）

#### 技术 46：NovelOS Foreshadowing Manager

- **链接**：https://github.com/perry121108-dotcom/NovelOS_
- **核心原理**：每个伏笔元素有独立追踪文件，记录首次出现章节、预期回收章节、状态标签（planted/revealed/abandoned）、关联线索列表。
- **昆仑可借鉴点**：昆仑 ontology 已有 Foreshadowing 实体（planted_chapter/status/priority/expected_reveal_chapter），但缺少"关联线索"和"揭示计划"的结构化管理。

#### 技术 47：Dramatica-Flow Hook Lifecycle

- **链接**：https://github.com/Decentralised-AI/dramatica-flow-enhanced-v4
- **核心原理**：伏笔（Hook）有完整生命周期管理——埋设→发育→临近→揭示→回响。每个阶段有自动预警，特别是"未回收线程"（unresolved threads）自动警告。
- **昆仑可借鉴点**：昆仑应将伏笔状态从三态（planted/revealed/abandoned）扩展为五态生命周期，并增加"逾期预警"（expected_reveal_chapter < current_chapter + 5 时触发提醒）。

### 6.4 能力/等级体系追踪

昆仑 ontology 已有 CultivationRealm 枚举和 Character.realm_timeline（[{chapter, realm, stage}]），这是较好的基础。增强建议：
- 增加"能力值时序快照"——不仅记录境界，还记录具体能力数值（攻击力/防御力/灵力上限等）
- 增加"物品-能力关联"——某角色的某能力来自某物品/某功法，图谱中建立关系边
- 增加"突破事件追踪"——每次突破的章节、原因、代价、副作用
