## 三、架构设计模式提炼

### 3.1 行业主流架构模式

```
模式1: 流水线串行 (Pipeline)
├── 代表: 昆仑(17步)、Novel-OS(5步)、AI_NovelGenerator(4步)
├── 优点: 逻辑清晰、可追溯、可断点续跑
└── 缺点: 串行耗时

模式2: 合同-提交 (Contract-Commit)
├── 代表: webnovel-writer
├── 优点: 强一致性、可审计、可回滚
└── 缺点: 实现复杂

模式3: 闭环迭代 (Audit-Loop)
├── 代表: InkAI(80分阈值闭环)、昆仑(Revise循环)
├── 优点: 质量自动提升
└── 缺点: 成本不可控

模式4: 事件驱动 (Event-Driven)
├── 代表: InkOS(守护进程)、昆仑(NATS消息)
├── 优点: 松耦合、可扩展
└── 缺点: 调试困难

模式5: 规格驱动 (Spec-Driven)
├── 代表: Novel Writer(Spec-Kit)
├── 优点: 需求清晰、AI友好
└── 缺点: 前期工作量大
```

### 3.2 最佳设计实践提炼

1. **三层规则分离** (InkOS首创): 通用规则→题材规则→书籍规则，逐层覆盖
2. **状态不可变快照** (Novel-OS): 每章生成后状态JSON版本化
3. **唯一事实源** (webnovel-writer): 创作前"合同"+ 创作后"提交"
4. **确定性引擎优先** (Novel-OS): 零LLM成本发现大量问题
5. **质量阈值闭环** (InkAI): 评分<80→定向改进→重评，直到达标
6. **上下文编译** (InkOS): 先编译规则栈和上下文，再写作
7. **多模型路由** (InkOS): 不同Agent可配不同模型
8. **BYOK** (NovelCrafter): 用户自带API Key，成本可控

## 五、差距分析

### 5.1 功能差距详解

#### 🔴 高优先级（必须补齐）

**1. 追读力系统**
- **现状**: 有爽点检测（pleasure模块），但缺少商业化追读力指标
- **标杆**: webnovel-writer 的 Hook（钩子）、Cool-point（爽点）、微兑现、债务追踪
- **方案**: 在pleasure模块扩展：
  - `hook_detector.py` — 章节钩子检测（开篇钩子/章末钩子/反转钩子）
  - `cool_point_scorer.py` — 爽点量化评分
  - `micro_payoff.py` — 微兑现追踪（短期承诺→兑现周期）
  - `debt_tracker.py` — 债务追踪（伏笔未回收=读者"欠债感"）

**2. 题材模板库**
- **现状**: 无题材概念，全靠Architect蓝图
- **标杆**: webnovel-writer 37题材 + InkOS 题材规则系统
- **方案**: 新增 `kunlun/genre/` 模块：
  - `genre_config.yaml` — 37+题材配置（玄幻/都市/言情/科幻/悬疑/历史/游戏/系统流...）
  - `genre_rules.py` — 题材专属规则引擎（禁忌/语言约束/节奏/审计维度）
  - 每个题材含：世界观模板、常见套路、禁忌清单、推荐节奏

**3. 三层规则分离**
- **现状**: 规则散落在各模块，无分层
- **标杆**: InkOS（通用~25条 → 题材规则 → 书籍规则）
- **方案**: 
  - L1 通用规则：从现有audit/style模块提取通用写作规则
  - L2 题材规则：结合新 genre 模块
  - L3 书籍规则：已有 `author_intent` + `story_bible` 雏形

#### 🟡 中优先级（尽快补齐）

- **方案**: 新增 `kunlun/cover/` 模块：
